# base_raw — prompt-matched base arm

Status log for the arm that removes the prompt confound between `base` and the four
discrete ablations. Appended as work lands, per the reporting contract.

---

## 2026-07-31 — why this arm exists

The four ablations were scored on a raw document prompt: no chat template, no roles,
no instruction, just the trained sentinels and label cues. `base` was scored on its
own chat template with an explicit English instruction. Every base-vs-ablation number
therefore mixed two variables — the model and the prompt it was given.

`base_raw` is the same stock Qwen2.5-Omni-3B on the ablations' prompt. The prompt
string is identical; the single substitution is inside the speech span, where the
waveform occupies the slot the unit block occupies:

```
ablations   <|speech_start|> u1 u2 u3 … <|speech_end|><|transcript_start|>
base_raw    <|speech_start|><|audio_bos|><|AUDIO|><|audio_eos|><|speech_end|>TRANSCRIPT:
```

### What this does not fix

The speech pathway. Base reads waveforms through its audio tower; the ablations read
discrete units. There is no configuration where both are on home ground:

- the discrete checkpoints have **no audio tower at all** — `model.py:600-605` sets
  `thinker.audio_tower = None` under `discrete_only: true`, which all four configs
  inherit from `omni_disc_base.yaml:8`, so there are no tower weights in the saved
  state dict to run;
- base has no embedding for the unit ids (its embedding stops at 151936; the units
  occupy 151936-152935).

So report `base` and `base_raw` as a bracket around the ablations. An ablation above
`base` is a prompt-independent result; an ablation above `base_raw` only is
prompt-conditional and must be stated as such.

### Sentinels are read as words, not tokens

Verified against the real tokenizer, not assumed:

```
'<|speech_start|>'     -> [27, 91, 88225, 4906, 91, 29]  ['<','|','speech','_start','|','>']
'<|speech_end|>'       -> [27, 91, 88225, 6213, 91, 29]  ['<','|','speech','_end','|','>']
'<|transcript_start|>' -> [27, 91, 1458, 1228, 4906, 91, 29]
'<|audio_bos|>' 151647   '<|AUDIO|>' 151646   '<|audio_eos|>' 151648
```

The three sentinels are ordinary BPE subwords for base — it reads "speech start" as
English, which is the most semantically meaningful thing available to a model that
never trained on the ids. The audio markers **are** native, so the tower splice is
exact. `<|transcript_start|>` has no native equivalent and became the plain cue
`TRANSCRIPT:`.

### Consequence: base echoes the delimiters

Because they are ordinary text, base sometimes continues the document by writing them
back out — e.g. `' <|speech_start|>If art solar of irishio knows hello and v Lola
again. <|speech_end|>'`. Those characters are scored like any other output; the
contract forbids post-processing, so they are **counted, not stripped**.
`sentinel_text_in_answer` was added to `discrete_eval_common._decode_report` as the
exact counterpart of `unit_ids_in_answer` (which base can never trigger, having no
unit ids), and `_wrong_modality` now fires on either. Without it one arm would look
cleaner than it is.

`launch_base_raw.sh` with `MULT=2.5 TAG=_mult2.5`, matching the budget behind
`*_numbers_final.csv`. Eight jobs (CLUAS, IWSLT, FLEURS × 6 conditions), each raced
across small-g and standard-g via `race_submit.sh` with the loser cancelled. All eight
won on small-g and started within 45 s.

The 2.5 rerun that produced the current `_final` numbers had no script behind it; the
multiplier is now a `MULT` parameter on both launchers, with `TAG` keeping a rerun at
a different budget from overwriting the file it should be compared against.

## What the numbers say so far

**The two headline ablation claims survive the fix.** AB4's Irish ASR (68.22) is
roughly half the error of base's best configuration (130.38), and its Irish→English
text translation (46.89) beats both base arms by ~20 chrF++.

**The fix does not uniformly favour the ablations, and one result moved against
them.** On IWSLT base scores *higher* on the ablations' prompt than on its own
(15.59 vs 14.00), so the ablations' deficit there widens rather than narrows. The
chat template was mildly disadvantaging base, not flattering it.

**The prompt swap helps base at transcription and hurts it at instructed tasks.**
`asr_ga` 219 → 130, but `asr_en` 3.77 → 20.42. Text translation barely moves
(27.41 → 25.26).

**One ablation result does not survive: AB1's Irish ASR.** Against `base` it looked
like a large gain (131.68 vs 219.03). Against `base_raw` it is 131.68 vs 130.38 —
indistinguishable. AB1 never learned Irish transcription; the apparent improvement
was the prompt, and continued text-only pretraining bought nothing here. This is the
clearest single vindication of running the arm, and it must be corrected wherever the
219.03 comparison was used.

Note the asymmetry in what the fix did: it removed one ablation claim (AB1 ASR),
widened the ablations' deficit on another benchmark (IWSLT), and left AB4's two
headline results standing. That spread is the evidence the correction was not
engineered to flatter the ablations.
